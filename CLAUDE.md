# CLAUDE.md

This file provides guidance to [Claude Code](https://claude.ai/code) when working with code in this repository.

Companion project: [`dropnext-monolith`](../dropnext/dropnext-monolith). Conventions here are intentionally kept uniform with that repo where it makes sense.


## Development Commands


### Build & Run

```bash
# Full build with tests
./gradlew build

# Build without tests
./gradlew build -x test

# Run application
./gradlew run

# Run tests only
./gradlew test

# Clean build (removes all build artifacts)
./gradlew clean
```


### Codegen — GraphQL & OpenAPI

```bash
# Re-download the Shopify Admin GraphQL schema (after bumping SHOPIFY_API_VERSION)
./gradlew graphqlIntrospectSchema

# Re-generate the typed Kotlin GraphQL client from the .graphql files in src/resources/
./gradlew graphqlGenerateClient

# Re-generate monolith DTOs from openapi.json (also runs automatically as a dependency of compileKotlin)
./gradlew openApiGenerate
```


### Development Environment

- Copy `.env.example` to `.env` and fill in `SHOPIFY_APP_CLIENT_ID`, `SHOPIFY_APP_CLIENT_SECRET`, `SHOPIFY_SCOPES`, `PUBLIC_BASE_URL` (use [ngrok](https://ngrok.com/) or similar for HTTPS).
- Optional: `ENABLE_TEST_HARNESS=true` exposes `/dev/test-harness` plus `/demo/*` routes.
- See the full env-var table in [README.md](./README.md).


## Architecture Overview


### Technology Stack

- **Language**: Kotlin 2.3.21 on JVM 25 (toolchain — Gradle downloads it).
- **Web Framework**: [Ktor](https://ktor.io/) (CIO engine).
- **HTTP Client**: Ktor + OkHttp (shared singleton; see `SharedHttpClient.kt`).
- **GraphQL Client**: [graphql-kotlin](https://github.com/ExpediaGroup/graphql-kotlin) — compile-time typed against the Shopify Admin schema (proxy: `https://shopify.dev/admin-graphql-direct-proxy/{version}`).
- **Serialization**: `kotlinx.serialization` (no reflection).
- **Logging**: Logback (`src/resources/logback.xml`) with MDC trace IDs.
- **Testing**: JUnit 5 with Kotlin power-assert and Konsist for architecture tests.

### Inbound webhook flow

1. Shopify POSTs to `/webhooks/shopify`.
2. `ShopifyRouting` verifies `X-Shopify-Hmac-Sha256` (constant-time compare) against the app secret.
3. Topic-specific handler runs:
   - `PRODUCTS_*`: parses body for resource id, runs `GetProductById` GraphQL query.
   - `ORDERS_CREATE`: if `MONOLITH_BASE_URL` is set, runs `GetOrderForDss` and POSTs to the monolith via `MonolithService`.
   - `ORDERS_UPDATED`: only syncs to monolith when `DSS_SYNC_ORDER_ON_UPDATED=true` (default off to avoid duplicate POSTs).

### DSS internal REST

Authenticated by `X-DSS-Internal-Secret` (when `DSS_INTERNAL_SECRET` is set) plus per-shop `X-Shopify-Access-Token` (or `DSS_SHOP_ACCESS_TOKENS` env map). Canonical spec: [`openapi.json`](./openapi.json). DTOs are **generated** by `openApiGenerate` into `dropnext.dss.lib.dss.dto` — do not hand-write them.

### Outbound monolith integration

`HttpMonolithService` is the single HTTP boundary to the monolith. `FakeMonolithService` (in `test/`) is the recording fake used in tests.

- Base URL: `MONOLITH_BASE_URL` (+ optional `MONOLITH_API_PREFIX`).
- Auth: optional `MONOLITH_API_KEY` (sent as Bearer).
- `DSS_ALLOW_INSECURE_MONOLITH=true` is **dev-only** — production rejects non-HTTPS monolith URLs at startup.
- Failures log to a dedicated WARN appender with `monolith_trace_id` for correlation.

## Development rules & conventions


### Testing

- Prefer **fakes** over mocks/stubs (functional, recording-style).
- See [docs/TESTING.md](./docs/TESTING.md) and [docs/TESTING_WITH_FAKE_SERVICES.md](./docs/TESTING_WITH_FAKE_SERVICES.md).
- Power-assert is preferred. Conversion guide:

  - `assertEquals(a, b)           →  assert(b == a)                                ` — Order reversed for readability
  - `assertTrue(x)                →  assert(x)                                     ` — Direct replacement
  - `assertFalse(x)               →  assert(!x)                                    ` — Add negation
  - `assertContains(str, substr)  →  assert(substr in str)                         ` — Use in operator
  - `assertNull(x)                →  assert(x == null)                             ` — Explicit null check
  - `assertNotNull(x)             →  assert(x != null)                             ` — Explicit non-null check
  - `assertThrows<T> { }          →  assert(runCatching { }.exceptionOrNull() is T)` — Catch and check type

- Architecture rules live in `test/dropnext/dss/ArchitectureTest.kt` (Konsist). Add a rule before introducing a new layer.
- Do **NOT** fix tests by broadening asserts. A failing well-designed test is more valuable than a passing meaningless one.


### Code style

- **2 spaces indentation** (defined in `.editorconfig`).
- **Use `val` over `var`** wherever possible.
- **Expression bodies** for short single-expression functions.
- **No `lateinit`** in production code; favor immutable `val` modeling.
- **Generic error messages in production**; verbose only in development.
- **2 blank lines between the import block and the first statement.**
- **Prefer `headerNames.forEach { headerName -> ... }`** over `for (...)` loops.
- **Naming**: plural-named functions return collections; singular-named functions return one item.
- **Extract common variables early** and **return early** when possible.
- Prefer proper imports + short names over fully qualified type references unless ambiguity needs to be avoided.


### API-related DTO conventions

- **snake_case JSON keys**: API-exposed DTOs use `snake_case` JSON field names. Kotlin properties stay `camelCase` — mapped via `@SerialName("snake_case_name")` on each multi-word property. Single-word properties don't need `@SerialName`.
- **Separate blank lines between properties** in API DTOs with `@SerialName` annotations (for readability).
- **API DTOs are always defined separately**: never reuse a generated OpenAPI DTO as an internal model or vice-versa.


### GraphQL queries

- Query files live in `src/resources/*.graphql`. The `graphql-kotlin` plugin generates typed Kotlin classes from them at compile time.
- After bumping `SHOPIFY_API_VERSION`, re-run `./gradlew graphqlIntrospectSchema graphqlGenerateClient` and fix schema drift.
- Keep `graphql.client.endpoint` in `build.gradle.kts`, `graphql.config.yml` (if present), and the `SHOPIFY_API_VERSION` env var in sync.


### Dependency policy

We prefer not to add any dependencies to the project. If it is important that a dependency is added, that should be mentioned as soon as possible (during planning or speccing). A human always has to accept that a dependency is added. Browse the internet to ensure you suggest the latest stable version (unless you have a good reason not to: state that reason clearly). When suggesting Java or Kotlin libraries, investigate if they --or their transitive dependencies-- make use of JVM reflection: state the findings.


### Reflection policy

As guarded against in `ArchitectureTest`: we do not use reflection in the project. Exceptions live in the test's allowlist.


### Implementation workflow

For small changes (typo fixes, single-line config tweaks, CSS, docs): just do the work and make sure tests still pass.

For non-trivial changes (new handlers, new outbound integrations, security-relevant changes): write a spec in `/specs/` first, then implement test-first (Red → Green → Refactor). TODO: align this workflow with the monolith's Verified Spec-Driven Development phases once the team agrees.


## Natural language instructions

- Full sentences: starting with a capital letter and ending with a period.
- No capitalization of every major word in headings/titles (e.g. "Code style" over "Code Style").
- Add particles (the, a, an, etc.) where natural.


## Documentation comments (KDoc)

One-line KDoc fits on one line:

```kotlin
/** Short doc comment. */
```

Not:

```kotlin
/**
 * Short doc comment
 */
```

Avoid comments that do not add value. A function `markFulfilled` with 3 simple statements does not need a KDoc saying "Marks as fulfilled" — that's noise.
